# ТЗ — Presentation: режим «Варианты сборки» + перенос Map + исправление Template Manager + адаптация

## 0. Роль исполнителя и главный принцип

Ты работаешь как **Senior Electron / Frontend Engineer + code archaeologist + regression engineer**.

Задача: **не переписывать Presentation**, а аккуратно расширить и исправить существующую программу. Сохранять текущую архитектуру, текущий рабочий функционал и существующий UI-контракт там, где он не указан к изменению.

Источники правды:
- **Presentation** — целевая программа, в которую вносятся изменения.
- **Sandbox_Styles_v8_WORKING(2).html + style-v8/** — поведенческий эталон для Map, адаптации и нормализации изображений. Sandbox не менять.
- **template-library-errors-2026-10-01.json** — реальный регрессионный материал по конфликтам библиотек.
- Перед изменением сначала провести аудит существующего кода и определить точки интеграции. Не создавать второй параллельный движок шаблонов/страниц, если можно переиспользовать существующие функции Presentation.

Главный критерий: после изменений старые сценарии Presentation продолжают работать, а новый режим использует **тот же стек/модель страниц**, а не отдельную несвязанную копию.

# 1. P0 — Новый режим Shell «Варианты сборки»

## 1.1. Новый режим

Добавить рядом с существующими режимами Shell отдельный режим:

**Название режима:** `Варианты сборки`.

Финальное короткое название уточнить перед публикацией (см. вопросы в конце).

Режим должен быть отдельной кнопкой в Shell и запоминаться так же, как остальные режимы.

При выборе этого режима Presentation iframe получает отдельный `SHELL_MODE`, а внутри Presentation открывается **собственный гибкий split**.

Переключатели Build Variants (`1 2 3 ...`) разместить **в верхней панели этого режима рядом с фильтрами Map**, компактно, как отдельную группу. Каждая кнопка показывает номер и, если задано, короткое имя варианта: например `1 — Черновик`, `2 — Clean`, `3 — Dark`. Рядом должна быть кнопка `+` для создания нового варианта. Вторая точка доступа — Build Manager в мобильной/Shell-панели.

**левая часть:** Map шаблонов;

**правая часть:** стек собираемой презентации.

Это НЕ тот же самый внутренний `Split` Sandbox, где показываются две карточки. Existing Sandbox Split-функция в новый режим **не переносится**.

## 1.2. Внутренний split Map + Stack

- Вертикальная разделительная линия между Map и Stack.
- Разделитель draggable/flexible: можно сделать Map шире или уже, соответственно увеличивая/уменьшая область Stack.
- Позиция split должна запоминаться так же, как другие пользовательские настройки.
- Map и Stack имеют независимую прокрутку.
- Колесо мыши над левой областью прокручивает Map; над правой — Stack.
- Длинные стеки и длинные карты не должны прокручивать всю оболочку.
- Сплит должен корректно работать на разных размерах окна.

# 2. P0 — Map в новом режиме: перенести поведение Sandbox практически 1:1

## 2.1. Что переносится

Map занимает всю левую часть нового внутреннего split и работает как полноценная рабочая карта. Не открывать вместо неё одиночный preview шаблона.

Перенести **только Map / Gallery**, без одиночного preview-режима Sandbox и без отдельного Sandbox Split.

Map должен показывать все доступные шаблоны с визуальными превью, а не только выбранный шаблон.

Основа поведения — существующий `map-v5.js` и соответствующая логика Sandbox.

В Sandbox сейчас есть сохранённые параметры `row`, `column`, `size`, `selectedOnly`; размер карточки ограничен 140–1200 px, gap по вертикали и горизонтали — 0–80 px. Карточки скруглены, сетка перестраивается автоматически. fileciteturn0file0L3545-L3575

## 2.2. Фильтры

Сверху Map оставить компактную панель фильтрации:

- фильтр по стилю;
- фильтр по категории;
- Favorites / Только избранные;
- Selected Only / Только отмеченные;
- количество доступных шаблонов;
- размер карточек;
- вертикальный gap;
- горизонтальный gap.

Логика фильтрации должна повторять Sandbox: стиль может быть одним или несколькими значениями, категория — одной или несколькими, избранные отсекаются отдельно, `selectedOnly` показывает только отмеченные шаблоны. fileciteturn0file0L751-L779

## 2.3. Обязательное поведение dropdown

Dropdown-окна фильтров всегда имеют **фиксированную ширину/высоту кнопки**.

Если выбрано несколько значений:
- кнопка не растёт;
- названия выбранных значений не должны раскладываться внутрь кнопки в длинную строку;
- внутри раскрытого списка видны галочки;
- закрытая кнопка сохраняет один и тот же размер.

Логика:
- `Все категории` = взаимоисключающий пункт: при его включении все остальные категории снимаются;
- выбор одной или нескольких отдельных категорий снимает `Все категории`;
- аналогично для стилей.

Не переносить ошибку текущего Sandbox, где выпадающие контролы могут разрастаться от длинных названий.

## 2.4. Размер карточек и gaps

Поведение оставить как в Sandbox:
- размер карточки меняется ползунком;
- вертикальный и горизонтальный gap — отдельные настройки;
- сетка автоматически перестраивается под доступную ширину;
- карточки сохраняют круглость/радиус и общий визуальный характер Sandbox Map;
- собственный scrollbar Map — минималистичный и в стилистике Presentation.

## 2.5. Перенос шаблона из Map в Stack

При наведении на карточку шаблона появляется кнопка-стрелка действия.

Есть два сценария:

### Обычная стрелка

Вставить шаблон в текущий Build Stack.

Правила:
- если в Stack выбран page/template — вставка происходит **после выбранного**;
- если ничего не выбрано — вставка в конец Stack;
- используется существующая page insertion logic Presentation, а не новая параллельная реализация.

### Ctrl + стрелка

**Заменить выделенный page текущим шаблоном.**

При замене использовать существующий алгоритм Presentation `applyTemplateToSelectedPage()`.

Критически важно сохранить при замене:
- пользовательский текст, который уже был отредактирован;
- назначенные/пользовательские изображения;
- `imageTransform`;
- page id и остальные нужные метаданные страницы.

То есть Ctrl+стрелка должна быть семантически тем же действием, что текущая замена шаблона в обычном Presentation.

## 2.6. Drag & Drop

Шаблон из Map можно перетащить мышью:
- прямо в нужное место Stack;
- либо на область действия стрелки.

Обычный drag-and-drop = вставка в указанную позицию.

**Ctrl + Drop = replace**: если во время Drop удерживается Ctrl и есть выбранная страница, текущая выбранная страница заменяется перетаскиваемым шаблоном по той же логике, что Ctrl+стрелка. При замене сохраняются пользовательский текст, изображения, transforms и нужные page metadata.

# 3. P0 — Stack внутри «Вариантов сборки»

## 3.1. Stack = обычный стек Presentation

Справа показывается обычный page stack Presentation в компактном режиме.

Для каждой страницы сохраняются все текущие элементы управления:
- номер страницы;
- Move Up;
- Move Down;
- Copy;
- Paste;
- Duplicate;
- Delete;
- AI (можно оставить текущую кнопку, отдельная переработка AI сейчас не нужна).

Не придумывать новый внешний вид страницы — переиспользовать текущие page controls Presentation и адаптировать только контейнер под новый split.

## 3.2. Поведение выбора

В Stack может быть выбрана одна страница.

Если выбрана страница, она становится target для:
- обычной стрелки из Map → вставка после неё;
- Ctrl+стрелки → замена её текущего шаблона.

Все обычные операции Stack работают именно с текущим активным Build Variant.

# 4. P0 — Варианты / Build Variants

## 4.1. Переключение вариантов

Добавить компактный динамический набор кнопок вариантов:

`1 2 3 4 5 6 ...  +`

Каждая кнопка переключает **отдельный стек презентации**. Для каждого варианта хранить номер и пользовательское короткое имя. Отображение: `номер + имя`, при отсутствии имени — только номер. Кнопка `+` создаёт новый свободный вариант и позволяет сразу задать его имя.

Важно: цифра = не фильтр и не страница, а отдельный Build Variant.

Количество вариантов **динамическое**. Не ограничивать систему шестью вариантами. Пользователь может добавлять новые варианты кнопкой `+`.

## 4.2. Активный вариант

В каждый момент времени есть один активный Build Variant.

При переключении вариантов:
- Stack перерисовывается из выбранного варианта;
- выбор страницы внутри варианта по возможности сохраняется отдельно;
- Map продолжает работать с общей библиотекой шаблонов.

## 4.3. Выход из режима

Критически важно:

Когда пользователь выходит из режима «Варианты сборки» в обычный Presentation / Editor / другой Shell-режим, показывается **последний выбранный Build Variant**.

Работа в обычном Presentation после этого должна идти **именно с этим стеком**.

Изменения, сделанные в обычном Presentation, должны сохраняться в этот же Build Variant, а не в отдельную временную копию.

Не должно существовать расхождения “Build Stack” vs “обычный Stack”. Активный вариант должен быть источником текущего финального стека.

## 4.4. Дублирование варианта

Добавить:

**Duplicate Stack / Дублировать стек**

Алгоритм:
- берём текущий активный Build Variant;
- полностью копируем его стек со всеми текстами, картинками, transforms, ручными правками и page metadata;
- переносим копию в следующий свободный номер варианта;
- новый вариант становится активным.

Если следующий номер занят — выбрать следующий свободный.

## 4.5. Переименование варианта

Каждый Build Variant должен иметь короткое пользовательское имя. Имя можно задать при создании через `+` и изменить позже из Build Manager/панели варианта. Номер варианта остаётся системным идентификатором позиции, имя — только display name.

## 4.6. Очистка варианта

**Clear Selected Stack / Очистить выбранный стек**

Очищает только текущий вариант.

Другие варианты не изменяются.

# 5. P0 — JSON Import / Export для Build Stack

Добавить в панель настроек режима «Варианты сборки»:

- Copy Stack JSON;
- Import Stack JSON.

## 5.1. Export

Export = JSON только **текущего выбранного Build Variant**.

Не экспортировать всю библиотеку и не экспортировать остальные варианты.

Использовать существующую внутреннюю модель страницы Presentation, чтобы round-trip был без потери данных.

## 5.2. Import

Import JSON должен:
1. разобрать JSON;
2. проверить структуру до изменения состояния;
3. проверить, что referenced template IDs существуют в текущем Template Registry;
4. если всё корректно — собрать новый стек;
5. сохранить порядок страниц и все текстовые/графические изменения.

При импорте **обязательно показать выбор целевого места**:
- существующий Build Variant;
- новый свободный Variant.

Не перезаписывать существующий вариант молча. Если выбран новый вариант — создать его и запросить/принять короткое имя. Если выбран существующий — явно показать выбранный номер/имя перед подтверждением.

Если есть несуществующие template IDs:
- не изменять частично целевой стек;
- показать список отсутствующих ID;
- импорт считать неуспешным целиком.

Цель: AI может получить набор доступных шаблонов и вернуть JSON собранного стека; Presentation должна загрузить этот JSON без ручной пересборки.

# 8. P0 — исправление Template Manager: конфликты одинаковых template ID

Это отдельная критическая задача, от которой зависит корректное отображение Map.

Реальный log показывает: загружено 5 библиотек, 320 template records, active=5, conflicts=112, при этом `errors=0`. У библиотек также отсутствует явный `libraryId`, и текущая реализация использует fallback по имени файла. fileciteturn0file1L11-L29 fileciteturn0file1L31-L47

Причина конфликта в текущем Presentation уже найдена в коде: `computeActiveEntries()` строит **глобальное пространство уникальных template ID** и пропускает последующие совпадения. Таким образом одинаковый template ID в разных библиотеках физически не может одновременно попасть в active registry.

Это нужно исправить.

## 8.1. Новое правило идентичности

Одинаковый исходный `template.id` в разных библиотеках — **не одна и та же запись**, если это разные библиотечные экземпляры.

Нужно перейти на библиотечно-скоупленную идентичность, например концептуально:

`libraryId + originalTemplateId`

Внутренний стабильный runtime ID должен быть уникальным и детерминированным.

При этом:
- исходные экспортированные Sandbox IDs не менять;
- Sandbox export не трогать;
- исходный ID хранить как source/original ID;
- новый runtime ID используется Presentation Registry для различения экземпляров.

## 8.2. Ключевое требование совместимости

Существующие страницы Presentation, созданные до миграции, не должны потерять связь с шаблоном.

Нужно сделать миграцию mapping old ID → owner/current record там, где однозначно можно определить владельца.

После миграции:
- старые страницы продолжают открываться;
- новые библиотеки с тем же исходным ID не блокируются;
- все варианты библиотек видны одновременно;
- один стиль не исчезает только потому, что тот же template ID присутствует в другом стиле/библиотеке.

## 8.3. Кнопка Normalization

В Template Manager добавить:

**Normalize IDs** / **Нормализовать ID**

Кнопка выполняет тихую нормализацию:
- без перезагрузки приложения;
- без сброса UI;
- без закрытия текущего документа;
- пересчитывает runtime IDs/registry mappings;
- перестраивает active registry;
- обновляет все панели и селекторы.

Нормализация не должна означать удаление дубликатов.

Здесь “дубликат template ID” = допустимое совпадение исходных ID между разными библиотеками; такие шаблоны должны остаться отдельными записями.

Настоящие повторения одного и того же ID внутри **одной физической библиотеки** можно продолжать валидировать отдельно.

## 8.4. Conflict log

После исправления конфликты не должны использоваться как причина скрытия шаблона.

Если полезно для диагностики, conflict log может показывать:
- одинаковый source ID;
- библиотеку;
- нормализованный runtime ID.

Но результатом Reload должен быть доступный активный template record из каждой включённой библиотеки.

# 9. P0 — короткие названия стилей и шаблонов

Сейчас Presentation может показывать технические имена/составные имена вместо коротких названий, которые пользователь видит в Sandbox.

Исправить отображение так, чтобы в UI использовалось **human-readable display name**, а не технический ключ.

## 9.1. Для стилей

Sandbox экспорт отдельных стилей содержит человеческое имя в служебном заголовке JS. Presentation должен при импорте читать этот display name, не меняя Sandbox export.

Логика fallback должна соответствовать существующей Sandbox `programStyleDisplayName / suggestedProgramStyleName`, а не придумывать новый формат.

## 9.2. Для шаблонов

В:
- Template Manager;
- Template Library;
- Map;
- dropdown выбора шаблона;
- page header/capsule, где выводится имя шаблона;

показывать короткий пользовательский `label`.

Не показывать по умолчанию составные технические значения вида `Category_ID-01`, если для записи уже есть нормальный human label.

Технический ID оставить доступным только там, где это действительно диагностическая информация.

# 11. P0 — полный перенос алгоритма Text Adaptation из Sandbox в Presentation

Это не новая упрощённая реализация. Нужно перенести **поведение Sandbox** и встроить его в существующую Presentation Text Panel.

Sandbox `adaptation.js` измеряет фактическую высоту текста через Range API, сохраняет индивидуальные исходные gaps между парами, не двигает shapes/images и не меняет font size; ручной диапазон идёт от первого до последнего выделенного текста. fileciteturn0file0L4460-L4498

## 11.1. Перенести функциональность

Обязательные возможности:
- Auto adaptation;
- ручная Adapt;
- Range / диапазонная адаптация;
- Normalize Selected;
- Normalize All как часть Adapt;
- Reset Layout;
- Copy Gap;
- Apply Gap;
- автоадаптация после редактирования текста;
- сохранение настроек;
- работа в single selection и multi-selection.

Не переносить внутреннее устройство UI Sandbox — переносится **логика**, а UI адаптируется к текущему дизайну Presentation.

## 11.2. Правила алгоритма

В точности соблюдать Sandbox:
- измерение фактической высоты живого текста;
- не уменьшать вручную увеличенный текстовый блок обычной Adapt, если измеренная высота меньше текущей;
- Normalize используется явно, когда нужна принудительная нормализация;
- каждая пара текстовых блоков сохраняет свой исходный gap;
- общий единый gap всему шаблону не назначать;
- если пара уже перекрывалась, использовать минимальный safety gap 8 px;
- соседние колонки не двигаются;
- shapes/images обычной Adapt не двигать;
- font size не менять.

Это соответствует текущему Planner Sandbox, включая `MIN_GAP=8`. fileciteturn0file0L4460-L4498

## 11.3. Range

При включённом Range:
- берётся первое и последнее выделение в визуальном порядке;
- все текстовые блоки между ними входят в диапазон;
- выше диапазона не измерять и не сдвигать;
- ниже диапазона не менять.

## 11.4. Copy Gap / Apply Gap

Sandbox требует ровно два текстовых блока одного шаблона.

`Copy Gap`:
- вычисляет расстояние между нижним блоком и нижней границей верхнего блока;
- сохраняет число в px.

`Apply Gap`:
- выставляет этот gap у выбранной пары;
- если нижний блок сдвигается, сдвигает нижележащие блоки, чьи X-области пересекаются с ним;
- делает это одним undo action.

Эта логика уже реализована в Sandbox. fileciteturn0file0L3899-L3938

## 11.5. Ctrl+Z — критическая правка

Каждое действие адаптации должно создавать **одну запись Undo**.

Ctrl+Z после Adapt:
- отменяет только действие адаптации;
- не меняет текущий template/page на другой;
- не сбрасывает выбранный Build Variant;
- не уничтожает текущие template bindings;
- не теряет текст или изображение.

Несколько Adapt подряд → несколько последовательных undo.

Undo/Redo должен работать в той же history-системе Presentation, без отдельного независимого history.

# 18. P1 — что делает обычный Presentation после выхода из Build Mode

# 28. Зафиксированные решения заказчика

1. Название режима: **«Варианты сборки»**.
2. Количество вариантов: **динамическое**. Есть кнопка `+` для создания нового варианта.
3. Варианты имеют **номер + короткое пользовательское имя**; имя можно задавать и менять.
4. Import JSON: **обязательно спросить**, импортировать в существующий вариант или создать новый свободный вариант.
5. Build Variants входят в **проектные данные** и сохраняются после полного перезапуска программы.
6. Floating popup настроек по `Alt+O` **полностью скрыть/убрать из UI**. Настройки перенести в Gear.
7. Drag & Drop поддерживает обе операции: обычный Drop = вставка, **Ctrl + Drop = replace**. Ctrl+стрелка также = replace.

Эти решения являются частью обязательного контракта и не требуют дополнительного согласования перед реализацией.
